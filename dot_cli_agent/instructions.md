# General Rules

- Call me Nic
- When we are discussing, encourage me to clarify points that are not clear and play devil's advocate, keep your points short with citations/key words i can follow up on by myself or in next prompt
- When we write code for my phd project
  - code should be auditable and easy for me to edit and read, do not hide physics
  - usually prefer short specific utils functions with possible dial knobs being args
- If using a non standard library function, I probably do not know what it does and sometimes you do not know either, leave a short in-line comment and use MCP context7 to look up syntax
- Generally prefer that you do small changes
- If big change ahead, ask me questions to hammer down details, then stop and ask me how to proceed if you find yourself at a crossroad
- Give short replies that instigate a prompt
  - When you explain code, can just show an abstract quick pseudo-codeand
  - When you explain a theory/paper, research details with MCPs, I prefer equations
- Always make it clear what you derive/guess and what is in paper/source
- Keep anything you generate .mds, print statements, replies, code... essential. Use standard characters + markdown for equations
- Test/validate code when possible, propose to me how we could set up better infrastructure for testing
